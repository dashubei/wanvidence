# 設計判断ログ 02: 執筆スタイルガイド

作成日: 2026-08-26
対象: 章の原稿（MDX）を書くすべての作業

---

## 1. 3層構造（全節で厳守）

| 層 | 実装 | 誰のためか |
|---|---|---|
| 第1層 | `<KeyPoints items={[...]} />` | 急いでいる人・初心者。**ここだけ読んで行動できる**粒度 |
| 第2層 | 本文 | 標準の読者。専門用語を避けた平易な日本語 |
| 第3層 | `<Deep title="...">` | 上級者。研究の中身・数値・サンプルサイズ・その研究の限界 |

第1層に書くのは「結論」であって「要約」ではない。
「社会化は重要です」は結論ではない。「生後◯週までに◯を◯回」が結論。

## 2. 専門用語

- 消さない。初出時に `<Term desc="平易な言い換え">用語</Term>` で包む
- 理由: 獣医師やトレーナーに相談するとき、正しい語を知っていること自体が武器になる
- `desc` は1行。長い説明が要るなら本文か Deep に書く

## 3. 解像度（最重要）

「重要である」で終わる文を書かない。以下のいずれかまで落とす。

- **数値**: 何週齢、何分、何回、何メートル、何度、何円
- **手順**: どの順序で、何をして、失敗したらどう戻すか
- **時間**: どれくらいで効果が出るか、途中で悪化する期間はあるか
- **失敗例**: うまくいかないのはどういうときか、そのとき何をするか

悪い例: 「社会化期にさまざまな経験をさせることが重要です」
良い例: 「生後3〜14週の間に、犬が自分から近づける距離で、1回5分以内、
　　　　週に3〜5種類の新しい刺激。怖がるサイン（後述）が出たら距離を取って終える」

## 4. リスクの書き方

**リスク記述の直後に、必ず対処法を置く。**
リスク情報だけを提示すると人は防衛的に回避し、行動が変わらないことが分かっている。
`<Callout type="danger">` を単独で置かない。必ず対処とセットにする。

## 5. エビデンスの表示

- 主張の直後に `<EvidenceBadge level="..." note="n=... / 20XX年" />`
- `note` にはサンプルサイズと年を入れる（分かる場合）
- 出典は脚注 `[^1]` で振り、章末に一覧
- **出典が確認できない主張は書かない**。書きたい場合は「確認できていない」と明記する

## 6. 体験談の扱い

- `<Experience>` の中にのみ置く。本文に溶かさない
- 複数の記録に共通するものは `<Experience common>` を使う
- 体験談から「〜すべき」を導かない。「こう語られている」で止める
- **論文の知見と体験が食い違う場合、食い違いごと書く**（これは依頼者の明示要求）

## 7. 論争の扱い

- `<Disputed>` を使い、`japan` と `intl` の両方を埋める
- 断定できないものは `verdict` で断定しない
- `ask` に「獣医師にこう聞く」の具体的な文言を入れる
- **法的義務・条例上の義務・単なる慣行を区別する**

## 8. トーン

- 「〜してはいけない」を減らし「〜するとうまくいく」に書き換える
- 各章に `<TodayAction>` を1つ置く（今日中に終わる作業）
- 最初の1週間で必ず成功する課題から始める順序にする
- 脅さない。ただし盛らない。都合の良い研究だけを集めない

## 9. MDX の書き方

- コンポーネントは import 不要（ルート側で注入済み）
- 使えるもの: `KeyPoints` `Deep` `Callout` `EvidenceBadge` `Experience` `Disputed` `TodayAction` `Checklist` `Term`
- `Checklist` の `id` は文書全体で一意にすること（保存キーになる）
- 表は普通の Markdown で書く（自動で横スクロール化される）
- frontmatter は `src/content.config.ts` のスキーマに従う

## 10. 禁止事項

- 出典のない数値
- 体験談の一般化
- 「〜と言われています」（誰が言ったのか書く）
- 断定できないことの断定
- 絵文字（アイコンは Lucide のコンポーネントを使う）

## 11. 調査ファイルのエビデンス表記を、5段階にマッピングする

追記日: 2026-08-26

調査エージェントは指示した5段階（強／中／弱／体験／論争中）から外れた表記を
使うことがある。実際に出てきたもの: 【中〜弱】【弱〜中】【強／一次情報】
【裏が取れず】【保存版】。

執筆時は次の規則でマッピングすること。**迷ったら弱い側に倒す。**

| 調査ファイルの表記 | 使うバッジ |
|---|---|
| 【強】【強／一次情報】 | `level="strong"` |
| 【中】 | `level="moderate"` |
| 【弱】【中〜弱】【弱〜中】 | `level="weak"`（**中間表記は弱に倒す**） |
| 【体験】 | `level="experience"` |
| 【論争中】 | `level="disputed"` |
| 【裏が取れず】 | **バッジを付けず、本文に「確認できていない」と書く** |

### バッジの密度について

調査ファイルにバッジが少なくても、**執筆時には主張ごとに付けること**。
69KBの調査ファイルにバッジが18個しかない、という状態が実際に起きている。
バッジがない主張は、読者にとって「根拠の強さが不明な主張」になる。

判断の目安: **数値・時期・効果・因果を述べた文には必ず付ける。**
一般的な説明や定義には不要。

### 「裏が取れず」と書かれた項目の扱い

調査エージェントが「裏が取れなかった」と正直に書いた項目は、
**隠さず、本文に残す。** ただし断定はしない。

書き方の例:
> 犬種によって吠えやすさに差があるとされますが、
> **この本の調査では、犬種ごとの具体的な数値を示す一次資料を確認できませんでした。**

これは弱点の告白ではなく、読者が他の情報源に当たるときの手がかりになる。

## 12. `<Disputed>` の japan / intl を、無理に埋めないこと

追記日: 2026-08-26

28章（保険か貯金か）を書いた執筆エージェントから、判断の確認要請があった。

> `<Disputed>` は japan/intl 両方を埋めるのが原則だが、この章の論争（保険 vs 積立）は
> 「日本の慣行 vs 国際指針」ではなく「条件次第」という性質のため、japan/intl は
> 空のままにし、二論点を本文（slot）に書いた。

**この判断は正しい。** 以下を規則として明文化する。

### 使い分け

| 論争の性質 | 書き方 |
|---|---|
| **日本の慣行と国際ガイドラインが食い違う**（ワクチン頻度、去勢時期、社会化と感染リスク） | `japan` と `intl` を両方埋める |
| **研究の結果が割れている**（カーミングシグナル、オキシトシン） | `japan`/`intl` は空。両論を本文（slot）に |
| **条件によって答えが変わる**（保険か積立か） | `japan`/`intl` は空。二つの見方を本文に。`verdict` で「どちらが正しいとは決められない」と明示 |

`japan`/`intl` が両方空なら、コンポーネントは左右の列そのものを描画しない
（`Disputed.astro` が `{(japan || intl) && ...}` で分岐している）。表示は崩れない。

### なぜ無理に埋めてはいけないか

**存在しない対立を捏造することになる。**
「日本ではこう」「海外ではこう」という枠に無理やり流し込むと、
実際には国際比較の問題ではないものを、国際比較の問題として読者に見せてしまう。
それはこの本が最も避けるべき種類の不正確さである。

### `ask` はどの場合も埋めてよい

論争の性質が何であれ、「専門家にこう聞くとよい」という具体的な問いは読者の役に立つ。
28章では、獣医師への質問を
「このサイズ・犬種で将来起こりやすい高額な治療は何ですか。その処置はだいたいいくらかかりますか」
とした。保険の判断に必要なのは保険の知識ではなく、**自分の犬に起こりうる医療費の見積もり**だからである。

## 13. MDX で不等号を書くときの落とし穴

追記日: 2026-08-26

21章の執筆時に、`p<0.01` という記述が **JSX のタグ開始と誤認されてビルドが落ちた**。

MDX は `<` の直後に英字が続くとタグの開始とみなす。統計値（`p<0.05`）、
体重条件（`10kg<`）、年齢（`<6ヶ月`）などで起きうる。

**書き方**: `&lt;` にエスケープするか、全角の「＜」を使う。
または「p は 0.01 未満」のように日本語で書く（読みやすさの点ではこれが最善）。

同じ理由で、本文中の `{` `}` も避けること（JSX の式展開と解釈される）。

## 14. `items` 配列の中に、コンポーネントを書かないこと

追記日: 2026-08-26

`<KeyPoints items={[...]} />` と `<Checklist items={[...]} />` の配列要素は、
コンポーネント側で **`set:html` によって生の HTML として挿入される**。
したがって **Astro コンポーネント（`<Term>` `<EvidenceBadge>` など）は展開されない。**

**この失敗はビルドエラーにならない。** ブラウザは未知のタグを無視して中身のテキストだけを
表示するため、**見た目は壊れず、機能だけが静かに失われる**（点線もポップオーバーも出ない）。
実際に3つの章で混入が起きていた。

### 書いてよいもの / だめなもの

| 書ける | `<strong>` `<em>` `<code>` `<a href="...">` などの素の HTML |
| 書けない | `<Term>` `<EvidenceBadge>` `<Deep>` などのコンポーネント |

用語解説を入れたいときは、`items` の中では `<strong>語</strong>（平易な説明）` の形にし、
**本文側で改めて `<Term>` を使う**こと。

### 検出方法

```bash
grep -o 'items={\[.*\]}' src/content/chapters/*.mdx | grep -o '<[A-Z][A-Za-z]*'
```

### 追記: Markdown 記法も `items` の中では機能しない

コンポーネントだけでなく、**Markdown の記法も展開されない**。
`items` は `set:html` で **HTML として**挿入されるため、Markdown の処理を一切通らない。

実際に起きたこと: 19章・20章で `items` の中に脚注参照 `[^4]` が書かれ、
**ページに生の `[^4]` という文字列がそのまま表示されていた**（計5箇所）。

| 使えない | 脚注 `[^1]` / リンク `[text](url)` / 強調 `**text**` / コード `` `text` `` |
| 使える | `<strong>` `<em>` `<code>` `<a href="...">` — つまり**素の HTML だけ** |

**出典を示したい場合は、`items` には書かず、本文側の同じ主張に脚注を付けること。**
第1層は「結論だけ」の層なので、出典は第2層以降にあれば足りる。

検出:
```bash
grep -o 'items={\[.*\]}' src/content/chapters/*.mdx | grep -oE '\[\^[^]]+\]|\[[^]]+\]\([^)]+\)'
```

## 15. 執筆指示と本書の原則が衝突したら、原則を優先すること

追記日: 2026-08-26

3章（あなたの条件で飼えるか）の執筆時、こういうことが起きた。

**指示**: 「1日に必要な世話の時間」を試算として示すこと。

**執筆者の判断**: 査読で裏付けのある総時間の一次統計が見つからなかったため、
**単一の数値を出さず**、内訳表＋自己記入形式にし、その理由を `<Deep>` で説明した。
「CLAUDE.md の『出典が確認できない主張は書かない』を優先した」と報告してきた。

**この判断が正しい。**

### 規則

執筆指示は、素材を読む前に書かれている。したがって
**指示が要求した数値・記述が、素材に存在しないことがある。**

そのとき:

1. **記憶から補わない**（最優先。これを破ると本書の前提が崩れる）
2. **指示を無理に満たさない**
3. **代替の形を考える** — 単一の数値が出せないなら、内訳表と自己記入欄にする。
   期間が特定できないなら、幅とその理由を示す
4. **なぜそうしたかを本文に書く**（読者にとっても有用な情報になる）
5. **報告で、指示から逸れたことと理由を伝える**

### なぜこの順序か

**指示は手段であり、原則が目的である。**
「出典が確認できない主張は書かない」は、依頼者がこの本に求めた第一の条件だった。
執筆指示はそれを実現するための道具にすぎない。道具が目的と衝突したら、道具を曲げる。

同種の判断は他の章でも起きている:
- 22章: 体験談の素材がなかったため `<Experience>` を使わなかった（体裁より正確さ）
- 24章: 催吐の具体手順が素材になかったため掲載しなかった（安全に関わる領域で特に重要）
- 29章: マイクロチップ住所変更の期限が素材になかったため書かず、警告を添えた
