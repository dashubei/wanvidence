## 判断1: 3層構造の被覆率が低かったので、補修した

初回の執筆で、章によって `<KeyPoints>`（第1層）の被覆率が大きくばらついた。

| 章 | 補修前 | 補修後 |
|---|---|---|
| 04 | 88% | 実質100% |
| 05 | 83% | 実質100% |
| 06 | **11%** | 100% |
| 07 | **18%** | 実質100% |
| 10 | **8%** | 実質100% |

**なぜ問題か**: 3層構造は依頼者が Q11 で明示的に選んだ設計で、「初心者から上級者まで
幅広く読める」を実現する中核の仕組みである。被覆率8%では、初心者が節を拾い読みできず、
実質的に第2層だけの本になってしまう。

**どう直したか**: 専用のエージェントを立て、**本文を一切変更せず**、各節の冒頭に
本文から抽出した `<KeyPoints>` を追加させた。同時に、本文中で研究の詳細・限界が
まとまっている箇所を `<Deep>` で囲ませた（文言は変えず、囲むだけ）。

**意図的に KeyPoints を置かなかった節**: 「まとめ」「この章の使いどころ」
「この章がやらないこと」——これらは節そのものが要約なので、結論を二重に置く意味がない。

## 判断2: 付録は手で書かず、本文から自動生成する

用語集・論争一覧・出典一覧を手で二重管理すると、**章を直したときに必ず食い違う**。
本文を唯一の情報源にし、`src/lib/extract.ts` が MDX を解析してビルド時に生成する設計にした。

- `<Term desc="...">語</Term>` → 用語集（同じ語は名寄せし、出現章へのリンクを付ける）
- `<Disputed topic="..." ... />` → 論争一覧（章の順に並べる）
- `[^key]: 本文` → 出典一覧（同じ文献は本文の先頭80字で名寄せ）

5章の時点で **用語61語・論争6件・出典158件**を抽出。章を書き足すだけで自動的に増える。

**この設計の副作用として得られたもの**: 出典一覧を眺めると、調査エージェントが
「著者名・正確な書誌情報は確認できず」と正直に書いた項目がそのまま並ぶ。
これは隠すのではなく、**この本の限界が一覧で見える**という点でむしろ望ましい。

## 判断3: 検証用の仮ページは、ページとして出さずにファイルだけ残す

`src/content/chapters/_smoke.mdx` は、執筆エージェントに「MDXの書き方の実例」として
読ませるために作った。全コンポーネントの使用例が入っている。

削除すると次の執筆エージェントが参照先を失うため、**ファイルは残し、`draft: true` にした**。
`[...slug].astro` の `getStaticPaths` が draft を除外するので、ページ生成もナビ掲載もされない。

**追記**: 全章を書き終えた時点で、このファイルは役目を終えたため削除した。

## 判断4: 執筆エージェントに WebSearch を禁止した

WebSearch 予算の枯渇という事情もあるが、より本質的な理由がある。

**執筆時に外部を調べさせると、調査ファイルにない情報が混入する。**
それは「出典が確認できない主張は書かない」という原則を、執筆段階で静かに破ることになる。
素材にないことは書かない、という制約はむしろ品質を守る。

今後の執筆エージェントにも、この指示を必ず入れること。

## 品質の実例（この水準を維持する）

07章の攻撃前シグナルの表は、9段階それぞれについて
「目で見て分かる特徴」と「そのとき何をするか」の2列で書かれている。
前足を浮かせたまま止まる／三日月形の白目／体重が前足側に乗る／垂れ耳犬種では
耳の付け根が前へ動く、といった観察可能な粒度まで落ちている。

同時に、**「この段階の順序自体を検証した研究は特定できなかった」という限界を明記し、
「それでも使う理由」を書いている**。断定できないことを断定せず、しかし読者を
実務的に見捨てない、という本書の狙いがよく出ている箇所。

## 追記（2026-08-26）: 出典の到達性を検証し、改善した

### 検証したこと

執筆された5章の脚注159件を、**原典に辿り着けるかどうか**で分類した。

| 分類 | 件数 |
|---|---|
| doi.org のURL付き | 28 |
| DOI番号は書かれているがリンクになっていない | 31 |
| その他のURL付き | 56 |
| 到達手段なし（書誌情報のみ） | 44 (28%) |

「本文の記述に疑いを持ったら原典に当たれ」というのがこの本の使い方なのに、
**28%は当たる手段がなかった。**

### やったこと

1. **DOI番号のリンク化**（32件）
   脚注定義行の `DOI: 10.xxxx/yyyy` を `DOI: [10.xxxx/yyyy](https://doi.org/10.xxxx/yyyy)` に変換。
   本文の記述は触らず、脚注定義行だけを対象にした。

2. **書誌情報しかない出典に検索導線を付けた**（45件）
   `src/lib/extract.ts` の `buildSearchUrl()` が、引用符で囲まれた論文タイトル
   （なければ著者名と年）から Google Scholar の検索URLを組み立て、
   出典一覧に「原典を探す」ボタンとして出す。

**結果: 158件すべてが、直接リンク（113件）か検索導線（45件）で原典に辿れる状態になった。**

### 途中で見つけた不具合

`lightMarkdown()` が、URL の中の DOI 番号に二重にリンクを張り、
href 属性を壊していた（`href="https://doi.org/10.1186/..." rel="noreferrer` が
リンクテキストの中に流れ込む）。

**原因**: 置換を単純に連鎖させていたため、前の置換で作った `<a>` タグの中身に
次の置換がかかっていた。

**直し方**: リンクを作るたびにプレースホルダへ退避し、全置換の最後に戻す方式にした。
順序は「markdown リンク → 素のURL → 素のDOI → 斜体」。

検証: 入れ子の `<a>` 0件、壊れた href 0件、未置換のプレースホルダ 0件。

### 意図的に残したもの

「（正確な書誌情報は本書の調査で確認できておらず、今後の確認を要する）」という
但し書きの付いた出典は、**そのまま残した**。
調査エージェントが正直に限界を書いた結果であり、隠すべきものではない。
出典一覧を眺めれば、この本がどこで裏を取れていないかが一覧で見える。
